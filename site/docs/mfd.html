.mfd import/export

Import a saved design to repair a mapping, or require an executable project. Export checks local compatibility; only an observed run in the reference application establishes its behavior there.

Import a design

From the repository root, try this XML mapping. It copies the input's Number field to the output's Value field:

cargo run -p cli -- import-mfd \
  --mfd crates/cli/tests/fixtures/executable-import/design.mfd \
  --out project.json --require-executable

Without --require-executable, recoverable constructs remain editable with warnings. Unsupported ownership or unsafe resource resolution can still stop an import.

Choose the appropriate boundary

  • Designs with sibling resources or catalogs: select a trusted root or manifest. Package resources take precedence; nested references stay under their authorizing root.
  • Byte packages: import without granting filesystem access.
  • Connected stages: use --pipeline when one XML target feeds a later stage.
  • Filename-driven documents: a connected filename is not a static preview path.

Check before exporting

cargo run -p cli -- export-mfd --project project.json \
  --out design.mfd --profile native-mfd --check --report-json

The check reports the proposed export without creating files. To publish the design and its schema or layout siblings, remove --check. The default ferrule-extensions profile and strict native-mfd have different admission rules. See export profiles and diagnostics and the conformance inventory for the exact feature and workflow.
